## 3. H1 — Church events can be driven through the running-event lifecycle

**Severity:** HIGH
**Status:** **Open** (top-5 patch P1, not applied)
**Known-issues pointer:** ISSUE-014

### Finding

`Event::canOpenRegistration()` (`Event.php:269`) checks only
`status === Draft && registration_form_saved_at !== null` — no
`event_kind` guard. Church events are created with `status = Draft`
(`EventController.php:279`). Any staff user can `POST
open-registration` on a church event, generating a public `/r/{slug}`
URL and walking it through `registration_open → closed → ongoing →
completed` while the UI reads `church_status`;
`AdvanceEventStatus` would auto-advance it.

`canEdit()`, `canEditRegistrationForm()` (`Event.php:242`) and
`RegistrationFormController::update` have the same gap.

Conversely, `EventController::update` (`:355-357`) sets
`church_status` with only enum validation — `ChurchEventStatus` has
no `allowedTransitions()`, so `Upcoming → Completed → Cancelled →
Upcoming` jumps are allowed with no audit.

Dashboard reinforces: church events (permanently `Draft`) appear as
"Draft — no registration form yet" action items
(`DashboardController::buildActionItems`).

### Fix

Add `! $this->isChurchEvent()` to the running-lifecycle guards (and
the mirror for church flows), and/or add transition rules + audit to
`ChurchEventStatus`.

## 4. H2 — No role checks in any church-module controller

**Severity:** HIGH
**Status:** **Open** (top-5 patch P9, not applied)
**Known-issues pointer:** ISSUE-015

### Finding

Zero `isAdmin` / `authorize` / `Gate` hits in all 12 church
controllers. Any authenticated staff user can create/update/delete
service occurrences, fellowship events/groups/attendance rows,
discipleship batches/sessions/enrollments/attendance — including
`FellowshipController::destroy` (`:165`), `ServiceController::
destroyOccurrence` (`:201`), `DiscipleshipBatchController::destroy`
(`:143`), `DiscipleshipEnrollmentController::store` (`:36`).

`docs/fellowship.md` admits "any authenticated user can perform any
action." The running-event side at least gates deletion by role/OTP.

### Fix

Admin gate or policies on destructive church-module actions before
production use.

## 5. M1 — `mark()` silently wipes a previously code-verified `verified_at`

**Severity:** MEDIUM
**Status:** **Open** (top-5 patch P3, not applied)
**Known-issues pointer:** ISSUE-016

### Finding

`AttendanceController::mark` (`:284-297`) calls `updateOrCreate(...,
['verified_at' => $verifiedAt])` where `$verifiedAt` is null unless a
matching code was submitted this request. Re-marking a code-verified
row (e.g., editing notes) without re-entering the code clears
`verified_at` with no audit trail — the "verified vs override"
distinction the end-of-event report is built on.

### Fix

Only overwrite `verified_at` when a code was submitted this request;
else preserve the existing value.

## 6. M2 — Admin `force_open` + deferred walk-in on a dateless event → 500

**Severity:** MEDIUM
**Status:** **Open**
**Known-issues pointer:** ISSUE-017

### Finding

`$event->event_date->copy()` is called unconditionally in deferred
mode (`AttendanceController.php:510-512` bulk, `:728-730` single).
`force_open` bypasses `canRecordAttendanceNow()`, the only guard
requiring non-null `event_date` (`Event.php:338-343`).

### Fix

422 when `event_date` is null and encoding mode is deferred.

## 7. M3 — OTP attempt counters are non-atomic

**Severity:** MEDIUM
**Status:** **Open**
**Known-issues pointer:** ISSUE-018

### Finding

Read-modify-write `Cache::get → Cache::put` in
`EventDeletionOtpService::verify` (`:85-120`),
`RegistrationDeletionOtpService` (same pattern),
`EmailTwoFactorService::verify` (`:60-90`). Concurrent wrong guesses
can exceed `MAX_ATTEMPTS = 5` before lockout triggers.

Cooldown itself is server-enforced; cache namespaces do not collide.

### Fix

Atomic `Cache::increment` on a dedicated attempts key, or a lock.

## 8. M4 — Unique-collision races → raw 500 despite friendly pre-checks

**Severity:** MEDIUM
**Status:** **Open**
**Known-issues pointer:** ISSUE-019

### Finding

Exists-check-then-insert with no try/catch:
`FellowshipAttendanceController::store` (`:98-138`, UNIQUE on
`(fellowship_event_id, participant_id)`),
`DiscipleshipEnrollmentController::store` (`:36-74`, UNIQUE on
`(participant_id, program_id)`), and `Participant::resolveFrom`'s
`firstOrCreate` (`Participant.php:171-219`) used by walk-in/bulk
paths. A concurrent insert between check and write throws
`QueryException` → 500.

**Note:** `resolveFrom` was rewritten for the composite rule
(2026-10-19, `composite-identity.md`). The rewrite preserves
`firstOrCreate` semantics, so the race window persists.

### Fix

Catch `UniqueConstraintViolationException` → 422, as
`RegistrationVerificationService::finalize` already does.

## 9. M5 — Anonymous registration-state enumeration in `begin()`

**Severity:** MEDIUM
**Status:** **Superseded by W5.1** (2026-10-19)
**Closed as:** top-5 patch P2, shipped

### Finding (historical)

`RegistrationVerificationService::assertNoDuplicateRegistration`
throws a revealing message to anonymous public users (`:526`): "This
email address or contact number is already registered for this
event." — an oracle for testing whether a contact is registered.
`finalize()`'s `identityConflict()` was deliberately non-revealing by
contrast.

### Resolution

W5.1 replaced the `begin()` message with the non-revealing form used
at finalize:

> This registration cannot be started. If you believe this is an
> error, contact the event organizer.

Recorded in `docs/registration-wizard.md` §5.5.

## 10. Low findings — L1 through L5

All **open** unless noted. Each maps to a `known-issues.md` entry.

### L1 — `resolveFrom` ignores email/phone cross-identity conflict

When both are supplied and match different participants,
`resolveFrom` matches by email only and silently ignores the phone
conflict — while `finalize()` treats the identical case as an
identity conflict. Walk-in/bulk intake can attach a phone belonging
to another participant's identity with no warning.

**Status:** Open. Documented as a known limitation in
`composite-identity.md` §7.3. **Known-issues:** ISSUE-020.

### L2 — Deletion dialog under-reports; inaccurate comment

`Event::relatedRecordCounts()` (`:214-225`) counts fields/registrations/
attendances but omits `registration_verification_challenges`
(cascade-deleted on event delete) — the admin confirmation dialog
under-reports what is destroyed. Also
`RegistrationDeletionController::performDeletion`'s comment
("survives the FK becoming null") is wrong — the row is deleted, not
nulled.

**Status:** Open. **Known-issues:** ISSUE-021.

### L3 — No unique index on `(service_type, occurrence_date)` + non-transactional recurring create

`ServiceController::storeRecurring` (`:135-197`) dedupes via
read-then-write `exists()` with no unique index and no transaction —
concurrent batch creation can produce duplicates; a mid-loop failure
leaves a partial batch.

**Status:** Open. **Known-issues:** ISSUE-022.

### L4 — `editParticipant` mutates shared cross-event identity

`RegistrationMonitorController::editParticipant` (`:269-292`) edits
the shared `Participant` (email/phone, unique-guarded) from one
registration, silently affecting all events and church modules for
that person; any staff can do it while the event is open/closed.
Documented as deliberate first-write-wins override, but it is a
footgun.

**Status:** Open. Documented in `composite-identity.md` §7.4.
**Known-issues:** ISSUE-023.

### L5 — Design-system informational items

The audit script is clean on hard rules, but Rule 5 (informational)
flags raw white utilities in 9 files. Spot-checks found `bg-white/5`
empty-state circles (`registrations/monitor/index.tsx:68`,
`show.tsx:378`) and `border-white/10` chips
(`attendance-filter-chips.tsx:88`, `events/attendance.tsx:558-569`).
Not hard-rule violations — design-review items at most.

**Status:** Open, cosmetic. **Known-issues:** ISSUE-024.

## 12. Verified as NOT errors (deliberate)

Recorded here so a future reader does not "fix" them:

- Event deletion ordered delete (attendances → registrations → event)
  is consistent with current FK schema. Dropped tables
  (`event_options`, `registration_options`) are not referenced.
  Church-module tables have no FK to events — no orphans on event
  delete. Participants never deleted (RESTRICT guards).
- Attendance-code alphabet, `SLUG_ALPHABET`, retry loops,
  `(event_id, attendance_code)` unique index, generation under event
  row lock — all match docs.
- Public form no longer calls `resolveFrom` — only walk-in/bulk paths
  do (`AttendanceController.php:619,736`).
- `User::$fillable` excludes 2FA fields. `contact_number_normalized`
  fillable but never written directly (mutator is sole writer).
- No `dd()` / `dump()` / `die` / `TODO` / `FIXME` / hardcoded secrets
  in `app/` or `config/`.
- `.env` not committed (only `.env.example`).
- `bootstrap/cache/` has no `config.php` (§13 rule respected).
- Firebase service-account dir absent (correctly gitignored).
